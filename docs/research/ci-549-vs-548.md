# CI run 549 vs 548: why the merge to main went red

Date: 2026-10-01. Scope: GitHub Actions workflow "CI", runs #548 (PR #364) and #549 (its squash on `main`), plus every failed CI run from #351 to #550.

## TL;DR

Run #549 failed because one CPU-bound jsdom test, `src/test/integration/accessibility-pages.test.tsx` > "Settings page" > "has a heading and renders without axe violations", took 5269 ms against Vitest's default 5000 ms test timeout. The same test, on the identical tree, the identical shard and the identical file order, took 4154 ms in #548. It was already at 83% of its budget, so ordinary runner noise decides pass or fail. There is no race, no PR-vs-push difference, and no shard effect.

21 of the 29 failed CI runs in the window have this cause: a "Test timed out" on a heavy jsdom test, almost always one that renders the Settings page or a Settings section. 2 more are a `waitFor` budget running out for the same reason. Each time, the fix raised one file's timeout or trimmed one test. None of them sized the budget against CI.

Confidence: high for #549 (direct log evidence). High for the historical classification (every failure log was read). Medium for the claim that #364 is what pushed this test over the edge: CI timings show a step change, but there is no local A/B.

## 2. Why #548 passed and #549 failed

Every structural explanation is ruled out:

- **Event differences: none that matter.** `.github/workflows/ci.yml` uses one job graph for both events. The only event-conditional line is `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` (ci.yml:12). No env, matrix, or cache key depends on the event.
- **Shard membership: identical.** Vitest's `BaseSequencer.shard()` sorts files by the SHA-1 of their root-relative path and slices them into equal ranges (`node_modules/vitest/dist/chunks/coverage.AVPTjMgw.js:2364-2374`). Same file set gives the same shards. Both runs report 158 files in shard 1. Inside a shard, `sort()` orders by cached results, then by file size (lines 2377-2403). CI starts without a Vitest cache, so the order is size-based and identical too. See also ["Vitest splits your test files, not your test cases, into shards"](https://vitest.dev/guide/improving-performance).
- **Coverage threshold: not involved.** Shards run with every threshold at 0 (ci.yml:85-88). The "Coverage gates" job was skipped in #549 because a shard failed.
- **Timing: this is the cause.** The test has no explicit timeout, so it gets Vitest's default of 5000 ms ([vitest.dev/config/testtimeout](https://vitest.dev/config/testtimeout)). Its CI durations:

  | Run | Commit | Settings axe test |
  |---|---|---|
  | #544 | 0fc1ab38 (pre-#364) | 3849 ms |
  | #545 | 768959ea | 3155 ms |
  | #546 | bc6029e3 | 2189 ms |
  | #547 | 017fe4f5 | 3627 ms |
  | #548 | #364 merge | 4154 ms |
  | #549 | 95085f22 (#364) | **5269 ms (fail)** |
  | #550 | 0df171a2 | **5071 ms (fail)** |

  Before #364 the test used 44-77% of its budget. After #364 it uses 83-105%. #364 rebuilt the Settings page: outline Tree, section menu, a card for every section (`git diff --stat 017fe4f5 95085f22`: `SettingsOutline.tsx` +203, `SettingsSectionMenu.tsx` +97, `SettingsSection.tsx` +80, 13 section files rewritten). That makes the render and the axe pass more expensive. #364 also changed this test's `waitFor` from `queryByText` to `getByRole("heading", …)`, which costs more in jsdom.

- **Runner variance is large.** Shard 2 ran the identical file list in 302 s of test time in #548 (centralus) and 587 s in #549 (westcentralus), 1.9x apart. `SpokenPunctuationSection.test.tsx` took 17.6 s in #548 and 40.8 s in #549. Shard 1 totals happened to match (541.87 s vs 542.20 s), so the 4154 → 5269 ms swing on this one test came from which files the 3 workers ran beside it, and from per-VM noise.

## 4. Mechanism

### 4.1 The #549 test (`accessibility-pages.test.tsx:526-541`)

Inside one 5000 ms budget, the test:

1. `await import("@/pages/Settings")` (line 528). The first import in this file of the whole Settings module graph (13 sections, dictation, shortcuts, sync), transformed and v8-instrumented. Its cost lands in this test. The next test in the same describe, which reuses the cached module, took 1473 ms in #549, against 5269 ms for this one.
2. `render(...)` of the full Settings page with React Aria.
3. `waitFor(() => getByRole("heading", { level: 1, … }))`. `getByRole` walks the DOM and computes accessible names and visibility.
4. `expectNoAxeViolations(container)` (`src/test/support/accessibility.ts:4-7`). This runs the full axe-core rule set over the page. jsdom has no layout, so every style lookup goes through jsdom's slow `getComputedStyle`.

One local probe on a 16-core host, an instrumented copy of the test, run alone with `--coverage`: import ≈ 400 ms, render ≈ 225 ms, waitFor ≈ 30 ms, axe ≈ 1470 ms. Without coverage: axe ≈ 800 ms. axe is about 70% of the cost, the import about 20%. Nothing waits on a timer or a promise race. It is all synchronous CPU.

### 4.2 Why CI is about 2x slower than a dev machine

- A public-repo `ubuntu-latest` runner has 4 vCPU and 16 GB ([GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). PR #303's body says "2-core runner". That is the private-repo spec and does not apply here (`gh repo view`: `"visibility":"PUBLIC"`).
- In run mode Vitest uses `availableParallelism() - 1` workers (`cli-api.B7PN_QUv.js:6951-6954`), so 3 jsdom workers plus the main process (v8 coverage, blob reporter) share 4 vCPU.
- CI always runs with `--coverage` (ci.yml:85). Locally that alone adds about 50% to this test (1369 → 2081 ms).
- Runners differ by region and VM: up to 1.9x for the same shard (section 2).
- The one local shard run pinned to 4 cores (`taskset -c 0-3 … --coverage --shard=1/3`) measured this test at 2206 ms, against 4154-5269 ms on CI. That puts CI at 1.9-2.4x local per test, in line with PR #362's "2.2x" estimate.

A test that takes more than about 2 s locally under coverage on 4 cores has no safe margin under 5 s on CI.

### 4.3 The same mechanism in the other recurring failures

- `SettingsRows.test.tsx:206`: the `describe` timeout is 30_000. "opens both collapsed blocks with Tab and Enter alone" walked the page with `user.tab()`. Every Tab is a userEvent keydown, a React Aria focus update, and a React re-render of a page with hundreds of controls. It took 15.4-16.8 s on CI and passed 30 s in #546. #364 now starts the walk near the target (`SettingsRows.test.tsx:264-275`).
- `SettingsRows` "falls back to the section heading" (`:357`) uses `waitFor(…, { timeout: 3_000 })`. Its default 1 s ran out in #538 and #539 because each focus request re-rendered every section (#362's diagnosis).
- `DictationSection.test.tsx:81` (describe timeout 15_000): "restores an off switch from persisted storage after a reload" takes 5.0-6.2 s on CI (#548, #549, #550 logs). It failed 7 runs in a row at 5 s (#465-#484).
- `SpokenPunctuationSection`: about 50 hidden controls get their visibility recomputed on every `getByRole` (#303's diagnosis).
- `Heatmap.test.tsx:58,90` (20_000 each): 365 React Aria grid rows (issue #263).
- `compact.test.ts`: a real VACUUM of a 50 MB Library. This is the only one fixed by shrinking the work (#287).

### 4.4 The one real race (#533)

CommandPalette navigates after `setTimeout(0)` and `flushPendingEdits()`, but the test asserted the path synchronously. #362 fixed it by waiting for navigation. It has not recurred.

The failure cannot be reproduced on this host: a 16-core desktop, even pinned to 4 cores, is about 2x faster per core than a hosted runner. That is expected for a budget problem and does not mean the test is healthy.

**Reproducing the CI environment cheaply, if needed:** run `docker run --cpus=4 --memory=16g` with `node:24`, `pnpm install --frozen-lockfile` and the exact CI test command. `--cpus` throttles CPU quota, unlike `taskset`, which only limits cores. To mimic a slow runner, add a CPU-burning sibling process (`stress-ng --cpu 1`). Pass criterion: every test stays under 50% of its timeout.

**CI-side diagnostic (preferred):** a `workflow_dispatch` job that runs the suspect files N times with the shard's command and uploads Vitest's JSON reporter output (`--reporter=json --outputFile=…`). That gives a real per-test duration distribution on hosted runners, per region, at no local cost.

## 7. Recommended permanent fixes, ranked

1. **Make the budget explicit and checked, not per-file.** Split `vite.config.ts` `test` into two Vitest projects: `unit` (default 5 s) and `integration` (whole-page renders: `src/test/integration/**` plus the Settings section tests). Give `integration` one deliberate `testTimeout`, derived from the measured CI p99 times a safety factor of at least 2. Then remove the per-file overrides. Ties to 4.2: the budget has to describe the slowest hosted runner, not a dev box.
2. **Add a headroom gate. This is the guard that keeps the class from coming back.** Have the shard jobs also emit `--reporter=json`, and add a small script in the coverage job that fails when any test used more than 50% of its effective timeout. It points at the test before it flakes, on every PR, deterministically. Pair it with a Vitest unit test, in the style of `src/test/unit/ci-workflow.test.ts`, that forbids timeout literals in `src/test/**` except in a short allowlist that names a reason. A bump then becomes a reviewed decision.
3. **Make the Settings tests cheaper.** This is the work that actually races the clock (4.1):
   - Move `await import("@/pages/Settings")` to the top level or a `beforeAll` in `accessibility-pages.test.tsx` (lines 528, 545, 562), so module load is not billed to the first test.
   - Run axe once per page, scoped to the page region, and share that render. Or pass axe `runOnly` with the rule tags this test needs (`wcag2a`, `wcag2aa`). axe is about 70% of the test (local probe).
   - In SettingsRows, DictationSection and SpokenPunctuationSection, render the section under test rather than the whole page, unless the whole page is the point. Resolve elements once, not per Tab (the #303 pattern).
4. **Product follow-up, optional.** The Settings page mounts all 13 sections eagerly. Rendering off-screen sections lazily would cut the cost in tests and on Android, but that is a product decision.
5. **Do not** add retries or `--sequence.shuffle` for this class. Retries hide a budget problem. Shuffle checks order dependence, and none was found: 548 and 549 ran identical files in identical order. Shuffle is still worth one periodic run as a separate isolation check.

## 8. Unverified claims

- **That #364's Settings rewrite is what moved this test from 2.2-3.8 s to 4.1-5.3 s.** To settle: run the probe test at `017fe4f5` and at `95085f22` under `--coverage` and compare import, render and axe times.
- **That within-shard worker co-scheduling, not VM speed, explains the 4154 vs 5269 ms swing in shard 1.** It rests only on identical shard totals (541.87 s vs 542.20 s). To settle: the CI repeat job from section 5, with JSON durations per run and region.
- **That a 2x factor plus 50% headroom is enough.** Shard 2 showed 1.9x variance between runners, and a worse runner could exceed it. The repeat job would give the real distribution.
- **That axe's cost is dominated by style lookups in jsdom.** The local per-rule probe showed no single dominant rule (largest: `hidden-content` 158 ms), so the cost looks like fixed per-run overhead. This was not profiled further.

## 9. What was built, and where it departs from section 7

Measured first: per-test durations from the Vitest blob reports of the last 9 CI runs (#544 to #552, 5,724 tests). 56 tests took over 5 s on CI, 31 over 10 s, 3 over 30 s; 34 used more than half of their own (already raised) timeout, and `SettingsRows` "opens both collapsed blocks with Tab and Enter alone" took 30.2 s against its 30 s raise. The budget problem is suite-wide, not a Settings problem, so the fix is too.

- **One timeout, not two projects.** `TEST_TIMEOUT_MS` = 60 s for every test and hook (`src/test/time-budget.ts`). 60 s is just under twice the pre-split `SettingsRows` duration (30.2 s). `SettingsRows` and the 216 s navigation sweep are now split; the 35 s Tutorial run has a 120 s exception. Post-split CI verification is recorded below. A timeout exists to stop a hang; a generous one costs nothing until a test hangs. A `unit`/`integration` project split would add config and change sharding to buy faster hang detection nobody asked for.
- **`waitFor`/`findBy*` default raised from 1 s to 10 s** (`ASYNC_UTIL_TIMEOUT_MS`). The two `waitFor` failures (#538, #539) were the same budget class. A wait returns as soon as its condition holds, so the raise only costs time on a test that is failing anyway.
- **The headroom check reports, it does not fail.** Section 7.2 proposed failing CI past 50% of the timeout. That is the same flake moved earlier: a test at 40% on a fast runner is at 76% on a 1.9x slower one. The reporter annotates and summarizes tests past half their timeout on the merged report; the timeout stays the only failure.
- **Overrides are refused, at runtime and in source.** The setup file fails any test whose timeout is not the suite's (one listed exception: the full Tutorial run, 35 s on CI, 120 s). A timeout literal in a test file needs a `// time-budget:` comment. All other per-file raises were removed.
- **The 216 s sweep was split**, one test per screen and per navigates flag (17 tests, longest 13 s locally).
- **Not done here:** making the Settings tests cheaper (section 7.3). Under the new budget they have room, and the reporter lists them on every run; that work is now a performance task, not a CI fix.

Verification on [CI run 36961284484](https://github.com/M4ss1ck/maibuk/actions/runs/36961284484): all 474 files and 5,759 tests passed with coverage gates enforced. The shard blobs contain 0 tests above half their timeout. The largest timeout share was 33.1% (19.9 s / 60 s, an unflagged navigation Command on a Note); the longest `SettingsRows` test took 8.6 s. These are measurements from one hosted run, not a guarantee about future runners.
